# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A single-script Python tool (`surfwindows.py`, stdlib only) that pulls Open-Meteo forecasts for wave-surfing spots (Netherlands, Portugal, Morocco, Türkiye) and ski resorts (Türkiye and the Alps), scores each hour 0–10, groups good hours into "windows", and publishes them as iCalendar feeds plus the data files for a static forecast page (`docs/index.html`). A GitHub Action runs it every 3 hours and commits the outputs. `README.md` documents the scoring rules for users. Keep it in sync when thresholds change.

## Commands

```bash
python surfwindows.py                          # live run: fetches every spot (a few minutes), overwrites the tracked outputs
pytest -q                                      # all tests (no network; the fetch is faked)
pytest -q tests/test_surfwindows.py::test_end_to_end   # single test
```

No dependencies beyond pytest. Don't add third-party imports to `surfwindows.py`. CI installs only pytest. There is no build step for the page: open `docs/index.html` in a browser (it loads `docs/data.js` with a script tag, so it works from `file://`).

To preview without touching the tracked outputs, call `run(load_config(), now, out_dir=<some temp dir>)` and copy `docs/index.html` next to the generated `docs/data.js`.

## Architecture / data flow

Settings live in `config.json`, surf spots in `spots.json` and ski resorts in `resorts.json` (one per line); `load_config()` merges them.

`run()` is the surf pipeline: for each spot `fetch_spot` → `merge` → `find_windows` (calls `score_hour`), then `merge_history` and the outputs. `run_ski()` is the ski one and runs after it even when the surf side fails: `fetch_resort` (one Forecast API call at the resort's `elev`) → `merge_ski` → `find_ski_windows` (calls `score_ski`) → `docs/cal/<resort>.ics` and `docs/ski.js` (`window.SKI`). Both fetch through `_fetch_all` (shared rate limiter, stops on `QuotaExhausted`) and carry over entries they could not fetch.

- **`merge`** joins marine hourly data (waves, from the spot's offshore `marine` coordinate) with weather hourly data (wind, weather code, temperature, from the `beach` coordinate) by timestamp. The marine request asks for several wave models (`MARINE_MODELS`), so keys come back suffixed with the model name. Per hour, wave height is the median across models (`wave_lo`/`wave_hi` keep the range, and a wide range lowers a window's confidence), direction comes from the finest model with data, and period is the median *peak* period (`_peak_period`: the model's own peak period, else the peak period of whichever of swell or wind sea is higher). Mean `wave_period` is only a last resort, because the scoring thresholds are for peak period and the default model returns no `wave_peak_period`. It skips hours with nulls, and marks daylight as sunrise−30 min through sunset. All stored times are UTC (`timezone: GMT` in the API calls); each spot's `tz` is used only for display.
- **`score_hour`** picks the thresholds from `PROFILES` by the spot's `profile` (`windswell` default, `groundswell` for the Atlantic). Height is first multiplied by the spot's `exposure` and by `swell_reach` (1 inside the swell window, fading to 0 at 60° outside it). Swell direction is judged against `good_swell_dir` (default: `swell_from` ± 60°, where `swell_from` defaults to `facing_deg`) and optional `blocked_swell_dir`; arcs run clockwise and can wrap over north (`in_arc`). Wind is judged against `facing_deg` (offshore = facing + 180). Hard vetoes: flat, short-period chop, waves travelling away from the beach, too big. It also sets `Hour.wind_kind` as a side effect. Tide and water temperature (`Hour.tide`, `Hour.sst`, a third API call per spot) are shown on the page only; they are not part of the score. Wave energy is computed on the page from height and period (0.5 × H² × T, in kW per metre of wave).
- **Horizon.** `past_days` (3) before today and `forecast_days` (14) are fetched and shown on the page. The past days are a hindcast scored with today's rules, there to compare the score with a session you actually had; they never go into the calendars. `data.js` keeps every hour for `hourly_days` (5) and every third hour after that; only windows starting within `calendar_days` (7) go into the calendar feeds.
- **`find_windows`** keeps runs of consecutive daylight hours with score ≥ `min_score` and length ≥ `min_window_hours`. Event UIDs are a hash of `spot_id` + start hour, so a window that moves or changes length gets a new UID. Each event links to its spot on the page (`feed_base` + `#spot=<id>`), in the notes and as `URL`; if the site moves, change `feed_base`.
- **Ski.** `merge_ski` splits precipitation into snow and rain from the temperature at `elev` (`snow_share`, `snow_ratio`), because the model's own split and snow depth are for terrain far below a ski area; depth is the larger of the model's and 60 % of the last week's snowfall there. `score_ski` works on lift hours (`LIFTS`, 09–16 local) with the step tables in `SKI`, which also go to the page. `fresh_cm` is the snow of the last 24 hours. Resort ids share `docs/cal/` with surf spot ids, so they must never clash (a test checks); `run()`'s clean-up of stale feeds knows both lists. The ski scoring is a first guess: there is no real-session test for it yet.
- **Calendar spots.** `calendar_spots` in `config.json` are the owner's own spots. Only they go into `docs/surf.ics`, `data/windows.json` (the history log, kept `history_days`) and `FORECAST.md`. `merge_history` replaces their future windows only when the fetch succeeded, so a failed fetch keeps the old ones. Every spot and every resort, calendar spot or not, gets its own feed `docs/cal/<id>.ics`; a failed fetch leaves that file untouched, and a spot removed from `spots.json` loses its file.
- **Outputs** (all committed by the bot, so don't hand-edit them): `docs/surf.ics` and `docs/cal/*.ics` (CRLF, RFC 5545 escaping and 75-octet folding via `ics_escape`/`ics_fold`), `docs/data.js`, `docs/ski.js`, `FORECAST.md`, `data/windows.json`. The feed URLs on GitHub Pages (`feed_base` in `config.json`; Pages serves them as `text/calendar`, raw.githubusercontent.com only as plain text) are what users subscribe to, so don't move or rename `docs/surf.ics` or `docs/cal/`.
- **The page.** `docs/index.html` is a hand-written static file (inline CSS and vanilla JS, no build, not generated). It reads `window.SURF` from `docs/data.js` (`to_data`): per spot, parallel hourly arrays (`score`, `wh`, `wt`, `ws`, …; `kind` and `day` are strings with one character per hour) plus that spot's windows, and the label thresholds from `PROFILES`. The left column is the summary (headline for "my spots", search, country tabs, spot list); the right column is the selected spot (day summary sentence, score by hour, wave height / period / wind charts). "My spots" are stored in the browser's `localStorage` and default to `calendar_spots`; subscribing is per spot: "Subscribe to calendar" next to the spot's name opens its feed links in place (`subHTML`, `toggleSub`), with no dialog. The forecast itself is shown either as a Windguru-style table of daylight hours (`tableHTML`, the default on phones) or as charts (`chartsHTML`); the choice is kept in `localStorage`. A small bar with the spot's name and the day buttons stay stuck to the top while a spot is scrolled. On phones the search field is the first thing on the page, and a menu button (next to it and in the stuck spot bar) opens `#menu`, which switches between surf and ski. The app is called Fish Forecast. A **Surf / Ski & snowboard** switch (`#modes`) swaps the whole page between two "worlds" (`worlds`, `enterWorld`, `switchMode`): `D`, `MIN`, `byId`, `countries`, `favs` and its `localStorage` key are reassigned, and every view that differs checks `s.ski` and hands over to a ski version (`skiDaySummary`, `skiSceneHTML`, `skiChartsHTML`, `skiTableHTML`, `updateSkiMap`, `skiSea`, `SKI_GUIDES`, all in the "ski and snowboard" block). Colours are registered CSS custom properties (`@property`) on `body`, with ski values under `body.ski`, so they animate when the class flips; JS-drawn chart colours come from `pal()`. The mode follows the spot id in `#spot=` (calendar links open the right side), else `#mode=`, else the last one used. The ski map uses OpenTopoMap tiles. While the charts show several days, the day under the pointer gets a band (`.dband`) and its day button is marked. The `i` buttons open guide cards (`GUIDES` in the script). The **Wave source** picker fetches one wave model straight from Open-Meteo in the browser for the open spot and My spots, and re-scores it with `scoreHour` in the page, a port of `score_hour` driven by the tables in `data.js`: change both together. `wave_models` in `config.json` narrows the bot's own blend. Times on the page are in the spot's own time zone. The small map loads standard OpenStreetMap tiles for the spot's `lat`/`lon` (darkened with a CSS filter; CARTO's free basemaps now need an API key); the wind and swell arrows are drawn on top by the page itself. `#spot=<id>` in the URL selects a spot; `#subscribe=1` (opens the spot's calendar links), `#menu=1`, `#guide=<key>`, `#tab=` and `#q=` exist for screenshots.

`run()` takes `fetch=` and `out_dir=` parameters so tests can inject fake hours and write to `tmp_path`. Spots are fetched in parallel (`fetch_workers`, default 6) behind one rate limiter (`MIN_GAP_S` between request starts) and `get_json` retries on HTTP 429 only for the per-minute quota and only within `WAIT_BUDGET_S`; on an hourly or daily quota it raises `QuotaExhausted`, the run stops fetching and publishes the spots it has (the others keep their previous entry in `data.js` and their old feed file), because Open-Meteo's free tier allows about 600 weighted calls a minute and one spot costs about 5.

## Gotchas

- The page takes its chart labels (flat / best size / too big / chop / swell) from `PROFILES` through `data.js`, but the day-summary wording and the guide texts in `docs/index.html` describe the scoring rules in words. When the rules in `score_hour` change, reread `daySummary` and `GUIDES`.
- Tests load the real `config.json` and `spots.json` and use a few spots by id as fixtures (`scheveningen`, `wijk-aan-zee`, `zandvoort`, `ribeira-dilhas`, `imsouane-bay`). Changing those spots' orientation, profile or exposure can break the scoring tests.
- The wind-swell thresholds come from real sessions in the Netherlands (e.g. the test about short-period swell being flat at the beach). The groundswell thresholds and most spot parameters (coordinates, `facing_deg`, `exposure`, `swell_from`) are estimates. When changing thresholds, add or adjust a test that captures the real-world case.
- Spot coordinates were sanity-checked against Open-Meteo's elevation data (sea within 2.5 km of the beach point, marine point at sea), not against a surf guide.
- The workflow (`.github/workflows/update.yml`) runs pytest before fetching, on cron every 3 hours (minute 17), on manual dispatch, and on pushes that touch `surfwindows.py`, `config.json`, `spots.json` or the workflow file. Bot commits are titled `forecast update <timestamp>`, so pull before pushing.
